## 一、开场 90 秒（先定位，别先讲技术）

> "这是一个 LLM 网关。企业内部接多家大模型时，会出现四个问题：成本失控、单厂商故障、多租户配额、以及没人知道钱花在哪。这个网关对上提供 OpenAI 兼容协议，对下适配多厂商，在中间解决这四件事。
>
> 我想强调一点：它不是 CRUD 项目。所有指标、连接池、熔断、配额这些老问题，在 LLM 场景下都有**新的约束**——比如响应是流式的、成本按 token 而不是按次计、一次调用秒级到几十秒。这些约束改变了很多'标准答案'，我讲几个具体的。"

这段的作用：把项目从"又一个中间件玩具"里拉出来，并且**主动预告有深度**，让面试官顺着你的钩子问。

## 二、六个技术点：结论 → 三层追问 → 可引用数字

### 1. 客户端断连 ≠ 上游停止生成（这个项目最硬的一题）

**结论**：虚拟线程被中断，并不会关闭 JDK HttpClient 的响应体连接。必须显式关流。

代码：`upstream/StreamAbortHandle.java`、`api/ChatCompletionController.java`（`abort` 那段）。

- **Q：客户端断开了你怎么知道？**
  A：SSE 是写时才感知断连。所以网关发了心跳（`stream-heartbeat-interval`，默认 2s），心跳写失败就取消上游。
- **Q：那心跳多久能发现？**
  A：实测（厂商沉默 9 秒、客户端第 1 秒离开）：无心跳 **8647ms**，心跳 2s **3396ms**，心跳 500ms **1396ms**。约等于 **2 个心跳周期**——第一次写进内核缓冲不报错，RST 回来后下一次写才失败。
- **Q：为什么中断不够？**
  A：这是我一开始的假设，而且是错的。最初只 `Future.cancel(true)`，三种心跳配置实测都是 ~8.6 秒，说明中断根本没释放连接。原因是 HttpClient 的阻塞响应体流不因 interrupt 关 socket。必须 `InputStream.close()`，所以我把这个句柄显式传进适配器。
- **追问到 JVM 层：虚拟线程上写 synchronized 有什么问题？**
  A：JDK 21 上阻塞的 `synchronized` 会 **pin 住 carrier thread**，正好抵消虚拟线程收益（JEP 491 才解决）。转发线程和心跳线程要互斥写同一个响应，所以 `SseWriter` 用 `ReentrantLock` 而不是 `synchronized`。

**主动认**：这个 bug 是我自己写完、想当然之后，靠"数上游模拟器活跃流数"量出来的。不是设计出来的，是测出来的。

### 2. token 配额：预扣 + 事后回补

**结论**：LLM 请求进来时不知道要花多少 token，所以配额不能按请求维度做。

代码：`ratelimit/QuotaService.java`、`ratelimit/TokenEstimator.java`。

- **Q：怎么估？**
  A：字符数 / 4 + CJK 逐字，**向上取整**。故意不跑真实 BPE：在网关热路径上逐请求做 tokenizer 是奢侈品，代价是前缀延迟。
- **Q：估不准怎么办？**
  A：拿到厂商 usage 后回补差额。实测一条流式请求：预扣 **515**，回补 **505**，实扣 **10**（厂商报的正好 8+2）。
- **Q：估少了呢？**
  A：记 `overage`，**不追认额度**。因为追认就等于配额可以被击穿，那这个上限就是假的；要修的是估算器，不是上限。
- **Q：客户端中途跑了，用量没有 usage 报告，怎么算？**
  A：按**已转发字节**推断（`forwardedChars/4`），不整笔退回。整笔退回等于让"放弃"免费，那放弃流就是刷额度的口子。
- **Q：缓存命中要不要占 token 预算？**
  A：不占，但仍占 rpm 和并发。因为命中的 token 是"省下的"不是"消耗的"；如果命中也扣预算，命中率一高配额就变成假象。

### 3. 熔断器：纯错误率在低流量下是死的

**结论**：打分路由会把故障厂商的流量分走，于是它的健康窗口永远攒不满样本，错误率判据**永远不触发**。

代码：`router/CircuitBreaker.java`、`router/UpstreamHealth.java`、`router/ModelRouter.java`。

- **Q：那你怎么发现这个问题的？**
  A：看指标。`gateway_circuit_transition_total` 计数是 **0**——故障注入跑了一轮，熔断器一次都没跳。
- **Q：怎么修？**
  A：加**连续失败判据**（默认 3 次）。错误率管高流量下的准确判断，连续失败管低流量下"至少要有结论"。
- **Q：修完之后呢？**
  A：完整生命周期被观测到：`CLOSED→OPEN` ×1、`OPEN→HALF_OPEN` ×4、`HALF_OPEN→OPEN` ×3、`HALF_OPEN→CLOSED` ×1。故障期 25 个请求只产生 **1 次失败跳**；纯"重试下一个"方案是 25 次。
- **Q：为什么半开探测要限制"已放行次数"而不是"在途次数"？**
  A：如果记在途，被放行但没回报的请求（客户端挂了、线程死了）会让熔断器**永久卡在 HALF_OPEN**。改成"放行的尝试数"，用完就重新打开，自愈。
- **Q：为什么不直接用 Resilience4j？**
  A：可以用，我选自己写是因为要控三件事：窗口是**时间桶**而不是计数桶（否则低流量下 12 秒前的样本还在算）、错误率要按样本量做**置信度收缩**、以及熔断要和打分路由共用同一份健康数据。这三点凑一起，读源码的成本低于改它的成本。

### 4. 打分路由：我推翻了自己三次

**结论**：调度算法的坑不在公式，在**冷启动和数据饥饿**。

代码：`router/ModelRouter.java#candidates`。

- **Q：打分怎么算？**
  A：`latencyWeight × 相对延迟 + errorWeight × 绝对错误率 + costWeight × 相对成本`，越低越优先；未观测的候选排在所有有样本的之前。
- **Q：为什么错误率不做归一化？**
  A：我一开始做了。两个候选时任何非零错误都被"除以最大值"放大成 1.0——等于把"一次被置信度收缩过的失败"和"彻底坏了"划等号。延迟和成本是无界的要归一，错误率本来就是 0–1。
- **Q：冷启动怎么处理？**
  A：试过"按已知均值假设 + 分数折扣 0.2"，结果该厂商 `window_requests=0`，**彻底饿死**，也就永远测不出真实延迟。改成硬规则：未观测优先。代价是每个厂商都要付一点预热流量。
- **Q：那低样本的错误率怎么办？**
  A：置信度收缩：`errorRate × min(1, volume / minVolume)`。1 次失败不该定罪；但收缩过头又会饿死，所以配合"未观测优先"和连续失败判据，三者是一套。

### 5. 缓存：一个字段过滤策略决定它是省钱还是埋雷

**结论**：字段过滤必须用**黑名单**，不能用白名单。

代码：`cache/CacheKeyFactory.java`、`cache/CachedResponseCodec.java`。

- **Q：为什么黑名单？**
  A：白名单会**静默忽略**网关还不知道的新参数，而新参数常常确实改变输出——那是缓存串味，最坏情况是答错还不自知。黑名单最坏只是多一次未命中。
- **Q：key 怎么算？**
  A：递归排序对象键、保留数组顺序（消息顺序有意义），SHA-256。`stream`、`user`、下划线开头的网关控制字段不进摘要——所以阻塞请求写入的条目，流式请求能命中（实测 `X-Cache: HIT`）。
- **Q：跨租户共享吗？**
  A：默认不共享，key 带租户前缀。共享能提高命中率，但 A 团队的私有上下文不该被 B 团队命中或反推。开关存在，默认安全。
- **Q：什么不缓存？**
  A：`temperature>0`（采样结果缓存=固化一次掷骰子）；`finish_reason` 是 `length`/`content_filter` 的（会把截断答案冻结整个 TTL）。
- **Q：命中率多少？**
  A：演示流量下 2%–40% 区间，取决于负载重复度，**我不给"平均命中率"这种数**——它完全由流量形状决定，给出来就是编。命中收益是 823ms → 6ms 且 `X-Upstream: cache` 证明没打厂商。

### 6. 计费落库：异步、幂等、可证明没丢

**结论**：队列上限管的是**延迟**，不是持久性。

代码：`billing/UsageLedgerWriter.java`、`billing/LedgerStore.java`、`resources/schema.sql`。

- **Q：队列满了怎么办？**
  A：`offer` 而不是 `put`——请求线程绝不等数据库。满了**落盘 JSONL**，不是丢弃。实测强行压垮（`queue-capacity=4` + 100 并发）：`written=73, spilled=27, lost=0`，合计正好 100。
- **Q：重启会不会重复计费？**
  A：`request_id` 是主键 + `INSERT IGNORE`，回放天然幂等。实测重启后 `replayed_rows=27`，总行数 117 → **144**，且 `rows == distinct_request_ids == 144`。
- **Q：怎么证明没丢？**
  A：`/v1/billing/reconcile` 三条等式，实测全部 `delta=0`：流水的执行 token == 指标 token；缓存 token == 节省 token；本进程流水行数 == 写入器自报条数。旁边摆着 `queue_depth`，所以瞬态差不会被误判成丢行。
- **Q：为什么用 JdbcTemplate 不用 JPA？**
  A："insert if unseen" 的批量语义 JDBC 本来就有形状；ORM 要么退化成 select-then-insert 竞态，要么在一批里堆几千个永不读取的实体。
- **Q：金额为什么存整数？**
  A：存**微单位**。浮点累加三万条价格来回答"这个月花了多少"会漂，而误差正好落在发生计费争议的地方。
- **Q：优雅关闭怎么做？**
  A：先让排空线程自然写完、超时才 interrupt。反过来会把一次干净关闭变成"还能写的行被推去落盘"——这个我一开始就写反了。

## 三、压测：我知道边界在哪，这比数字重要

| 并发流（5 秒/条） | 直连厂商 TTFT | 经网关 TTFT | 网关净增 | 错误 |
|---|---|---|---|---|
| 64 | 22ms | 87ms | +65ms | 0 |
| 256 | 59ms | 347ms | +288ms | 0 |
| 512 | 175ms | 586ms | +411ms | 直连 51 / 网关 127 |

内部计时拆分（512 并发流）：**admission 均值 5.7ms**，网关自身代码（非流式）**2.75–3.0ms**，内部 TTFT 300ms 对直连 185ms。

**两个我提出、然后被数据杀掉的说法**（主动讲，这是加分项）：
1. "出站连接被池化串行" → 实测 64 并发对应 **64 条 ESTABLISHED**，错。
2. "每 token 两次 JSON 编解码是主因" → 同样 5 秒流把 chunk 从 50 砍到 5，TTFT 只从 819ms 变 665ms，错。

**明确说出的局限**：压测机、网关、厂商模拟器同机（16 核、3 JVM），512 流错误数在不同轮次 0–127 之间波动。所以我**不声称测出了并发上限**，只声称：256 条长流零错误、同步代码开销毫秒级。剩下 ~360ms 缺口需要 JFR 定位。

## 五、边界与"我不会"（提前准备，别被动）

- **Redis/Lua 分布式配额未运行验证**：本机没 Redis。算术抽到 `TokenBucketMath` 被单测证明，Lua 是它的转录，条件装配 + 内存兜底。**被问到就直说没跑过**，然后讲你怎么保证等价性。
- **语义缓存没做**：误命中代价是"答错"，需要离线评测集校准阈值才敢上。
- **多实例部署没做**：单进程验证过，没上 K8s。
- **JFR 归因没做**：知道缺口在哪一层，没定位到方法级。
- **面板窄屏没验证**。

回答模板：**"这块我没做/没验证，原因是 X。如果要做，我的方案是 Y，成本是 Z。"** 比硬编一个答案强得多。

## 六、八股映射表（把任何问题拐回项目）

| 八股问题 | 项目里的落点 |
|---|---|
| 虚拟线程原理 / 注意事项 | 转发线程模型；`synchronized` pin carrier（JEP 491）；中断不关 socket |
| `synchronized` vs `ReentrantLock` | `SseWriter` 用锁的真实理由，不是背口诀 |
| 令牌桶 vs 漏桶 | 令牌桶允许突发；容量=突发上限、refill=速率，见 `BucketConfig` |
| 缓存穿透/击穿/雪崩 | 只缓存确定性请求；TTL + 容量上限；未命中打厂商 |
| 幂等 | `request_id` 主键 + `INSERT IGNORE`；重试不双计费 |
| 分布式一致性 | 内存桶与 Redis 桶的等价性；两层限流的组合语义 |
| 熔断三态 | 时间桶窗口 + 连续失败 + 有界半开探测 |
| 线程池/连接池 | `HttpClient` 复用（每请求新建会废掉连接池）；Tomcat `max-connections` 与长连接 |
| GC/内存 | 每请求 deepCopy + 双重序列化；流式不缓冲全量 |
| 可观测性 | 指标/日志/追踪分离；admission 与 forwarding 分开计时才有意义 |
| 计数器和 gauge 的区别 | 面板吞吐靠差分；未触发计数器显示 `—` 而非 0 |
